## How to spot AI-assisted commits
The early commits, while Claude did the work, carry a `Co-Authored-By: Claude ...` trailer; many also append a `Claude-Session:` line. Since GLM took over, every commit made with AI help ends with exactly `Assisted-by: glm-5.2 (Z.ai GLM) via Claude Code`, merge commits included. The loop's iteration commits (`e7b6a21`, `4f7c49e`) are the exception: they carry no trailer, only a `Generator:` line recording the generator's note. The post-review commits after `v1.0.0` were made by Claude and carry `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Nothing in the history is unattributed: every commit carries one of those markers. Even the steps I gated myself — the contract relock (`744e0b3`) and the Phase 0 merge into `main` (`2094df6`) — were committed by the orchestrator on my approval, so they carry the trailer too.

## Where I intervened / what I'd distrust
- **Decisions get a review too.** Before approving Phase 0's decisions, I asked for an independent check against the specs. It showed that two decisions I had been told were "spec-only" or "edit and relock" were really bigger changes.
- **Ask one question per concern.** Four separate questions turned out to be one design problem: whether the review signal can be trusted. Treating them as one produced measurements instead of opinions.
- **The visual signal measures less than its number suggests.** In the Phase 0 baseline, before any widget existed, a page whose only content was a heading still scored 63.5 on visual. Even the improved signal can be beaten by redrawing the reference with markup. It is a soft signal, weighted modestly, and the contract tests and accessibility checks carry more weight.
- **Anti-cheat checks need the whole page in scope.** The first guards only inspected the widget, and an overlay painted beside it defeated them. An independent reviewer found this, not the implementers.
- **The lock checks itself.** G4 catches careless edits to the harness. Deliberate ones are caught by the separation check and by people reading the diff.
- **Review before you lock.** The first review fixed what it found, but a second pass over the whole branch, just before the relock, found that the fixes had moved the weak points rather than removed them: checks that run inside the process they protect, and lists of things to refuse that a newer browser can outgrow. Where possible the new checks look at the result (what is painted, what is on disk) instead of listing what is forbidden.
- **I delegated one approval** (the Phase 0 plan) to Claude, on condition that it found no major problems. The plan's status line says so.
- **The checkpoints stayed mine.** I relocked the contract myself after reading the 71 files it named, and I approved the first merge into `main`. The overnight build ran inside decisions I had already accepted; nothing merged until I was back. For the later phases I delegated the merge go-ahead, gated on every check passing plus a clean review, but the final triage, the `v1.0.0` tag and the push to GitHub stay with me.
- **A reviewer is only as independent as its context.** The phase reviews were fresh subagents, but fresh context is not a fresh model: GLM was reviewing GLM. So I asked for an independent review of the Java branch as well — fresh and read-only, though it too ran on GLM, which is the honest limit of this setup. It confirmed there were no blockers, found one real major (a property test that was almost entirely vacuous) and three minors, and I had all four findings fixed and re-verified.
- **Re-measure what an agent reports.** One implementer closed its package reporting 92 tests; the measured count was 97. A subagent's summary is testimony, not measurement, which is why the orchestrator re-ran every check itself — the counts in this file are the measured ones.
- **The small decisions still came to me.** Skipping the optional Java extension was my call, and so was renormalising `mvnw.cmd` to LF once the line-ending attributes had landed.
